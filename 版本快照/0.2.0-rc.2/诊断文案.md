# 诊断文案与 Config 形状快照（`0.2.0-rc.2`）

> 中文 ｜ [English](diagnostic-text.en.md)

**文案会变，机制不会。** 排查时先按指南 §10 的"原因"列定位，本文件只用来对照"你那边是不是同一句"。

## 安装返回里的原样输出

| 场景 | 原样输出（本版本） |
|---|---|
| 模块**解析**失败（`_init` 阶段抛，零 import 时通常是顶层代码或 `Config` 校验） | `dsh: warning: 1 entry did not activate` + `<行id> (<包名>): failed to import`（**无 stack**，是兜底文案） |
| 模块加载成功、`apply()` 里抛 | 同上第一行 + `<行id> (<包名>): TypeError: …` + **完整 stack**（`at <你的函数>`） |
| 手写的"像 Standard Schema"的 `Config`（普通对象，不是原生 schemastery） | `TypeError: Cannot read properties of undefined (reading 'validate')` + stack（`resolveConfig` → `Fiber._resolveConfig` → `Fiber._reload`） |
| 已装状态下再 `install_bundle` | `{"stage":"install", … "error":{"code":"ambiguous-install"}}`（**不是失败，是没有变化可提交**） |
| 未认证请求打到自己的路由 | 你的 handler 自己返回的 `401` + 你自己的 JSON（如 `{"ok":false,"error":"unauthenticated request"}`） |

## `Config.listConfigs` 的 `status`

✅ 源码 `dsh-tool-cordis` `0.2.0-rc.2` 的 `liveConfig()`：

| `status` | 含义 |
|---|---|
| `schema` | 模块已导入，且读到了**原生** `Config`（`Config[Symbol.for('schemastery')] === true` 且带 `type` / `meta`） |
| `inactive` | 行存在但未激活 |
| `absent` | **没有** `Config` 导出（本指南的推荐形态） |
| `unsupported` | **有** `Config` 但形状不对 → 设置页渲染不出表单 |
| `tree` | 该行是 group / 子树，不是插件 |

> 新版本可能新增取值。**遇到不认识的 status**，按"模块已加载但另有问题"处理，
> 并去读那个版本的 `liveConfig()`（`dsh-tool-cordis` 里搜这个名字）。

## 顺带记下的环境事实

- 桌面端日志目录 `%APPDATA%\@deepseek-ai\dsh-desktop\logs` **存在但为空** →
  `logger` 输出看不到，"失败要让人知道"必须并进返回给调用者的报告。
- `remove_bundle` 后 `Config.listConfigs { name }` 返回**空目录**（行确实离开了 Loader 树）。
- Windows 上卸载后 `node_modules/<scope>/<name>` 的 **junction 可能残留**（pnpm 清理行为，无害）。
